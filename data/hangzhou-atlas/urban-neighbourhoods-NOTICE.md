# 杭州来源街区组团候选 · v0.16

`urban-neighbourhoods.json` 是从随包地理资料离线计算的**可选展示布局**。候选矩形、组团中心和组号均为制图生成结果，不是真实住宅小区、商业项目、土地权属地块或测绘建筑。模型表现可在这些范围中组织楼群与庭院，但不能把展示组件称为逐栋实景还原。

这份资料的呈现范围为WGS84 `[119.78,30.06,120.46,30.58]`，同时裁在原杭州市界内；没有修改市界、湖河、DEM、道路、森林、机场或景点锚点，也没有给来源以外的土地增加城市用途。既有 `urban-building-clusters.json` 已是邻近来源建筑的概括支持范围；本步骤沿用它，**没有再向外扩张或跨缺口连接来源土地**。

## 来源与生成

依赖随包文件：

- `scene-data.json`：市界、水体、森林、现有城地范围与道路。
- `source-classifications.json`：既有明确土地使用类别。
- `urban-building-clusters.json`：已归档建筑衍生的显示支持范围。
- `urban-ground-cover.json`：明确自然与开放地类。
- `../airports/hangzhou.json`：杭州萧山机场边界。

每份输入SHA-256、生成器SHA-256、Python/Shapely版本、投影和处理参数写在 `sources` 与 `processing` 中。© OpenStreetMap contributors；来源交付为OpenFreeMap / OpenMapTiles。既有地理资料和本衍生布局须保留ODbL署名及相关许可要求；原创生成代码和独立3D资产仍按各自MIT许可说明分发。

在项目目录，使用Python 3.12与Shapely 2.1.2运行：

```sh
python3 scripts/build-hangzhou-neighbourhoods.py
```

脚本可使用工作区已有 `work/china-atlas-data/python-deps`，也可使用自行安装的Shapely。仅读取上述随包资料，不访问网络或依赖原始瓦片归档。`--data`、`--airport`、`--bounds`、`--output` 可指定同格式输入和目标，`--max-per-group` 限制每个来源连通组的候选数量，默认32；这不是跨城市自动生成完整GIS资料的工具。

算法顺序：

1. 同类来源面合并，与已有城地并集和市界求交。不同明确类别的重叠部分单列 `mixed`；城地中未匹配明确类型的范围单列 `unknown`。不把医院、学校、工业或未知土地重新解释为商业/住宅。
2. 扣除水体、已知森林、park/grass/farmland/scrub/wetland等明确开放地、机场与主路走廊。motorway/trunk/primary全宽为110/90/65 m，另留单侧12 m，沿原中心线；来源隧道不切地表，桥梁路线仍排除。所有可用边界再向内退0.5 m以保护序列化后的接触边界。
3. 连通的同类可用面成为一个 `sourceGroupId`。优先采用附近真实主路沿线方向，其次采用来源面的长轴；一组确定方向后，组内所有候选继续使用同一方向。
4. 尝试宽1000/850/650/520/430/350/280/220/200 m、深宽比1/.85/.65的矩形，按面积由大到小。先求四角及边中点都可容纳的中心域，再以完整多边形包含判定检查整个矩形与孔洞，不能只靠中心或四角安全。已选矩形之间留16 m；没有可用候选的来源组保持未建设状态。
5. 对实际序列化坐标重复检查来源包含、障碍交叉、相互重叠和参数重放。它仍是有界贪心搜索，不是最大容量或最优填充的证明。

## 数据接口与单位

顶层 `neighbourhoods` 保存候选，`groups` 保存去重后的来源支持范围。

```js
{
  id, sourceClass, sourceGroupId,
  coordinates: [longitude, latitude],
  widthMeters, depthMeters, angleRadians,
  alignmentBasis,
  alignmentSegment: [[longitude, latitude], [longitude, latitude]],
  footprint: [[longitude, latitude], /* 四角并闭合 */],
}
```

`groups` 中每项有 `id`、`sourceClass`、`sourceRings`（外环及孔洞）、`areaMeters2`、`moduleIds`和共同方向依据。组号是来源计算标识，不是行政区或实际小区名称。`sourceClass` 保留住宅、商业、零售、工业、院校医疗等细分类，以及 `mixed`/`unknown`；消费端选择通用模型不能改变该来源语义。

尺寸严格匹配现行杭州实例工厂的本地米制：以 `scene-data.bbox` 的西、南为原点，经度单位为 `111320 * cos((south+north)*π/360)`，纬度单位为111320。当前MX为96525.36894699122、MY为111320。角度从该平面的正东向正北计；`alignmentSegment` 始终与矩形**宽度轴**共线，不会把另一条近路方向误当宽轴。消费端可由这段经纬度在自身不变投影中重新取得实际方向；不要将米制尺寸直接当作Web Mercator单位。

## 本轮候选数量与限制

最终数据包含3,502个候选、2,871个来源组，其中住宅2,281、商业68、零售20、工业551、院校215、医院14、mixed11、unknown342。增加220和200 m档后，较紧凑的真实来源地块也能承载完整组团；没有扩大来源土地。计数不是运行时必然生成的模型数量：较大坡差、地标/机场模型保留空间、真实渲染道路或完整模型足迹不合适时，运行时可以继续拒绝候选。

650 m以上的大型住宅组团支持范围很少，商业更少；因此不能把1,300 m的显示风格网格当成可放置的真实街区。较小候选可组成来源连续、方向协调的整体，仍不得填满未知地域或跨道路、林地和水面。复用组件里的庭院、绿化和广场是代表模型的概括，不是新生成的GIS公园、水体或真实工程设施。

地理候选通过不等于最终3D模型已通过。运行时须再检查实际投影/Float32尺寸、最终资产完整占地、真实地形整底支撑、实体主路、邻近模型和景点保留空间；来源矩形不能替代这些检查。用户视觉确认、实际浏览器几何与来源数据验证分别记录。
